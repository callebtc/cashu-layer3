Ecash on top of an unsettled HTLC

CASHU
LAYER 3

A Lightning payment to the mint is accepted and then held. While it sits pending, a Pointcheval–Sanders credential for the whole HTLC changes hands through private swaps. The last holder burns it to pay any invoice. Only then does the original payment settle.

STACK 
L3PS credential   alice ─▶ bob ─▶ carol      private swaps, no LN traffic
L2held HTLC       payer ═▶ hops ═▶ mint      ACCEPTED, unsettled, P unknown
L1bitcoin         channel outputs            CLTV bounds how long it can hold
FLOW

One HTLC, three holders, one settlement

The regtest topology from the README: a payer funds the mint's hold invoice, the claim moves Alice → Bob → Carol by swap, and Carol burns it into an unrelated invoice. Step through it or let it loop.

      Owner secret s authorizes spending. Its nullifier N = s·G_NULL is what the mint marks spent, so the receiver must swap before the token is theirs: the sender still knows the old s until its N is burned.
      
        
      Preimage P is not a swap witness and is never sent in a swap request. It rides along as bearer data so whoever finally burns can hand it to the mint, which needs it to settle the held payment.
      
        
      Consequence: every past holder knows P. That is harmless only because settlement also requires a valid, unspent credential, and the mint is the only party that can use P against the hold.

      CRYPTO
      PS credentials over BLS12-381
      
    
      Scalars mod q, the BLS12-381 group order. Mint key (x, y_h, y_s), a single key for every amount. Primitives were extracted from cashu-nft and adapted; signing of committed messages follows §6.1 of The Landscape of Pointcheval–Sanders Signatures.
      
    
      
      
      ISSUE · PUBLIC, AFTER ACCEPTED

      H = SHA256(P)
h = SHA256(dom ‖ amt_be64 ‖ H) mod q
C = s·G1                     + PoK(s)
u = k·G1                     k fresh, secret
v = k·[(x + y_h·h)·G1 + y_s·C]
      
        
      The mint computes h from the funded quote, so the client cannot pick an amount. dom = "Cashu_PS_HTLC_Claim_v2".
      
      
      
      
      WHY K MUST BE FRESH

      with u = G1:
  v* = v + (h* − h)·Y_h1      any claim
with u = k·G1:
  need y_h·u = k·Y_h1         CDH in G1
      
        
      A fixed base turns the public Y_h1 into an attribute-rewrite oracle. Mint-chosen k closes it; later rerandomization by the client gives privacy.
      
      
      
      
      SPEND · PRIVATE SWAP REQUEST

      u′  = ρ·u            v″ = ρ·v + o·u′
κ_h = h·Y_h2 + o·G2  U_s = s·u′
N   = s·G_NULL       B  = h·Y_h1 + t·G1

e(v″, G2) = e(u′, X2 + κ_h) · e(U_s, Y_s2)

π_own: U_s = s·u′        ∧ N = s·G_NULL
π_eq : κ_h = h·Y_h2+o·G2 ∧ B = h·Y_h1+t·G1
      
        
      Both proofs bind C_new = s′·G1, which carries its own PoK. h is shown equal across G2 (κ_h) and G1 (B) without being revealed. N is invariant under ρ and o, so rerandomizing cannot dodge the spent set.
      
      
      
      
      REISSUE · ONE ROUND TRIP

      U     = k·G1
V_raw = k·[x·G1 + B + y_s·C_new]
V     = V_raw − t·U
      = k·[(x + y_h·h)·G1 + y_s·C_new]
      → σ(h, s′)
      
        
      The mint consumes N and returns (U, V_raw) in the same POST /v1/swap response. The client strips t. The earlier two-round flow, which first fetched a signing base, survives only for recovering saved requests.
      
      
      
      
      BURN · PUBLIC h

      req   = { amount, presentation(h, N, π ⟂ amount ‖ invoice), invoice, P }
check   SHA256(P) = H,  h = SHA256(dom ‖ amount ‖ H),  invoice.amount = amount
reserve N, H, payout_hash              one sqlite txn
pay(invoice) → P′,  SHA256(P′) = H′    mint fronts liquidity + fees
persist receipt  →  settle(P)          crash-safe, no double payout

      WORKS
      What the design gets right
      
    
      Seven properties that hold in the current code.
      
    
      
      
      +Custody shrinks to the burn
      Until a burn, the mint holds an accepted HTLC it cannot settle: P only arrives inside a burn request. It can refuse service or cancel, which refunds the payer, but it cannot pocket the sats while tokens circulate. Classic ecash puts the mint in custody from deposit to withdrawal.
      
      
      +Transfers cost zero Lightning
      n swaps add no HTLCs, no routing fees, no liquidity movement. One POST /v1/swap, one round trip.
      
      
      +Swaps hide the claim
      Rerandomized PS plus a blinded h, under one key for all amounts. A swap reveals neither H nor amount, so its anonymity set is every live claim.
      
      
      +Double-spend check holds
      N = s·G_NULL depends only on s, so two rerandomizations of one credential carry the same N. It is consumed in the same DB transaction that issues the replacement.
      
      
      +Known forgery paths closed
      Fresh k defeats the fixed-base attribute shift. Amount and H are hashed into h, so relabeling breaks the pairing. The burn proof binds amount and invoice.
      
      
      +Pays any invoice
      The payout hash is independent of H. The final receiver runs a stock Lightning node and never learns Layer 3 exists.
      
      
      +Crash-safe redemption
      Burn is an outbox: reserve, pay, verify the payout preimage, persist the receipt, settle. A restart reconciles against the node's payment record instead of paying again. Exact retries return the original receipt, and only a definite payout failure releases the token. Exercised against LND regtest.
      
    
      
  
      

  
      
    
      NEEDS WORK
      Where it breaks or leaks
      
    
      Ordered by how much they limit the scheme, not by how hard they are to fix.
      

    
      
      
      CRITICAL
      
        
      Expiry is invisible
      
        
      A token is only worth something until the backing HTLC's CLTV runs out, minus the node's cancel margin. The mint does not set cltv_expiry, so this is LND's default final delta: hours to about a day, not weeks. The deadline is not in the token and not a signed attribute. The swap cannot check it because the mint never sees h, and a receiver can only check liveness by revealing H. A dead token swaps successfully.
      
        
      Sign an expiry epoch as a third attribute and prove it is in range at swap, or publish per-epoch sets of live claims and prove membership.
      
      
      ALICE · HTLC HELD · BACKED
      

      
      CRITICAL
      
        
      Every token is a held HTLC on other people's channels
      
        
      Each hop from payer to mint locks liquidity and one of its 483 HTLC slots for the token's whole life. To routing nodes that is indistinguishable from slow jamming, and hold fees or reputation schemes would price it out or filter it. L3 capacity is capped by how many long-held HTLCs the network tolerates.
      
        
      Fund via the mint's own channel or an LSP that accepts the hold explicitly; budget a hold fee into the quote.
      
      
      ONE HOP · EACH TOKEN PINS A SLOT
      

      
      HIGH
      
        
      The burn is custodial at the critical moment
      
        
      The mint receives P before it pays the payout invoice, so it can settle the hold and not pay. The earlier same-hash burn was atomic like a routing hop, but required the payee to know P. Separately, the mint can cancel the hold at any time. With the original payer as an accomplice, that is a clean double-spend against the current holder.
      
        
      Make the payout path release P only on proof of payout (PTLC or adaptor signature) once Lightning supports it; until then treat the mint as a custodian at burn.
      
      
      P REACHES THE MINT FIRST
      

      
      HIGH
      
        
      The endpoints are linked
      
        
      Issuance reveals H, amount and C. Burn reveals H, h, amount and P. The mint maps every funding payment to its payout invoice exactly. Whole-claim amounts are often unique, which makes timing and amount correlation trivial.
      
        
      Burn with h hidden and prove SHA256(P) consistency in ZK, or settle through a batched or delayed path that breaks the 1:1 mapping.
      
      
      SWAPS ARE FOG · BOTH ENDS SHOW H
      

      
      MEDIUM
      
        
      Whole claims only
      
        
      No split, merge or change. A 12,345-sat token pays exactly a 12,345-sat invoice. Routing fees on the payout are absorbed by the mint up to fee_limit_sat; the protocol has no fee field and no revenue model for the liquidity the mint fronts.
      
        
      Move the amount into a committed attribute with range proofs so one claim can fan out into several credentials.
      
      
      TOKEN AMOUNT MUST EQUAL INVOICE
      

      
      PROTOTYPE
      
        
      Not production code yet
      
        
      One commit, about 5k lines of Python and 64 tests. The adapted PS construction and Σ-proofs are unaudited. The cashuPS token is not NUT-compatible, so ordinary Cashu wallets cannot read it. One server process per database. The mint needs outbound liquidity to front every payout.
